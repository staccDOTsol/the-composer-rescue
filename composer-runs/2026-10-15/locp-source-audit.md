All **308** authorities from the sampled token-account census are 296-byte `VestingEscrow` accounts owned by Locp with discriminator `f477b704497487c3`. The exact on-chain offsets (including eight-byte discriminator) are:

## Exit paths and observed first blockers

The SDK IDL exposes eleven instructions. The ones relevant to existing vault outflow are `claim`/`claim_v2`, `cancel_vesting_escrow`, and `close_vesting_escrow`; `update_vesting_escrow_recipient` can redirect a future claim only if its mode authorizes the signer. `create_vesting_escrow` and `create_vesting_escrow_v2` fund a new escrow from the sender. `create_vesting_escrow_from_root` requires a matching Merkle proof and moves tokens from a root escrow into a new vesting escrow; `fund_root_escrow` adds tokens to the root. None of these latter paths provides a withdrawal from the 308 existing escrow PDAs. `claim_v2` requires the stored recipient as signer, stored mint, noncancelled state, and the escrow's matching ATA; the token program checks the destination mint. The destination token account need not be owned by the recipient in the reference code, but the recipient must authorize that choice. Cancellation uses mode bits `1=creator`, `2=recipient`, with `3=either`, and constrains its payout accounts to the stored creator and recipient. It transfers currently vested tokens to the recipient and the remainder to the creator, then closes the vault. `close_vesting_escrow` requires the stored creator and, if uncancelled, full claiming; it can return only incidental residual vault tokens after the scheduled claim is complete.

Current-binary `simulateTransaction` tests used WET escrow `BtZ8jPfdN8mVmok3x55He1CMwdS1xWpXBTMTigsjVH3Q`, cancel mode 1, creator `G9E6nB4ZDdfyKrg3FJuGvMrGQE2cXnuAEKR1ECQUiPXu`, recipient `A8t1fdhaftyUZ1iBxCGJ681SE79Atzuxnk9t4bKzxznj`, and **existing distinct payout token accounts**. Results in [simulation JSON](locp-source-exit-simulations.json), reproducible with [script](locp-source-exit-sim.js):

| Route | Current-binary result | First blocker or payout |
| --- | --- | --- |
| Creator-signed cancellation, counterfactual unsigned simulation | Succeeds | 320M raw WET vault closes; 80M to recipient, 240M to creator |
| Outsider signer attempts cancellation | Fails | 6005 `NotPermitToDoThisAction`, `vesting_escrow.rs:161` |
| Creator signs cancellation but creator payout aliases recipient token account | Fails | 2015 `ConstraintTokenOwner` |
| Creator closes before full claim | Fails | 6019 `ClaimingIsNotFinished`, `close_vesting_escrow.rs:63` |
| Outsider tries close | Fails | 2001 `ConstraintHasOne` on stored creator |
| Creator updates recipient, counterfactual unsigned simulation | Succeeds | Only recipient field changes; vault balance does not |
| Outsider updates recipient | Fails | 6005 `NotPermitToDoThisAction`, `vesting_escrow.rs:170` |

The positive controls deliberately disable signature verification and **do not imply access to the creator key**. Failed simulations return null post-account snapshots from this RPC, so the nulls are not evidence of deletion. The actual program's instruction failures are in the logs. A flashloan-funded transaction can supply temporary tokens and instructions; it cannot manufacture the stored recipient or creator authorization or change mode-0 permissions. The lock's integer schedule and cumulative claimed counter, rather than share price or debt accounting, govern repeated claims. This source and direct-gate audit does not establish a profitable composition; separate current-binary atomic flashloan simulations are needed for that conclusion.

## Recipient-selected destination and off-curve signer provenance

A separate current-binary read-only test used YZY escrow `AHYBvim1ebpaTrKdhVg5svFTpuSrMCSF1D88K5F1r7pd`, whose stored recipient is `8XePxHs4ypF3e2NhonvFiyprb9fjEZnHQtyGLWCBoATz`. With signature verification disabled, a counterfactual **recipient-signed** `ClaimV2` sending 1,000,000 raw YZY units to the **creator-owned** same-mint ATA succeeded: vault decreased 1,000,000, creator ATA increased 1,000,000, and escrow `totalClaimed` increased 1,000,000. This validates that the deployed `ClaimV2` lets its authorized recipient select a same-mint destination. Replacing the recipient signer with the creator failed first with Anchor 2001 `ConstraintHasOne`; setting destination equal to the source vault failed 6006 `InvalidRecipientTokenAccount`. Two consecutive authorized 1,000,000-raw claims in one transaction succeeded, with exactly 2,000,000 raw total debit and `totalClaimed` increment. The positive cases are unsigned simulations and establish **no access to the real recipient's key**. [Claim simulation JSON](locp-source-claim-destination-simulations.json), [reproducer](locp-source-claim-destination-sim.js).

The three largest nominally claimable sampled escrows total **$106.85M** at stale census marks; all three are YZY escrows with the same **on-curve** recipient. Among the 19 sampled escrows with at least $1M nominally claimable each, **10** have off-curve recipients, totaling **$56.89M** in marked claimable tokens. All 10 recipient addresses currently exist as System-owned, zero-data accounts. Account ownership alone therefore does not identify their PDA signer. The [Squads V4 vault-check endpoint documented by Squads](https://docs.squads.so/main/development/api/vault-check) returned `{isSquad:true, version:"v4"}` for each of the 10; [Squads' vault documentation](https://docs.squads.so/main/development/typescript/accounts/vault) explains why these vault PDA accounts can be uninitialized or System-owned while the Squads program signs their transactions. One historical successful DBR outflow provides direct signer provenance: transaction `Pp94BjG7zg9EGKKRRw2NGLJDQU2W8gEv6ac7RaVZnypcJLY98NDzrn2oSwibDWB5fCUhxXN5PvBLVKkfJVNc1Bz` at slot **380739286** invokes Squads V4 `VaultTransactionExecute` at the top level, Locp `ClaimV2` by CPI at stack 2, and the token transfer at stack 3. Its off-curve recipient `3fbKXhU8oeKEUiL5vXp1BKf6F2v57D5G8dCNwhnSAEvv` is not a transaction signer in the outer message; successful inner `ClaimV2` establishes the Squads-signed vault route. [Recipient provenance JSON](locp-source-recipient-provenance.json), [reproducer](locp-source-recipient-provenance.py), [sampled outbound trace set](locp-outbound-signer-traces.json).

For an outsider-directed claim from one of these off-curve recipients, directly substituting an outsider signer for the stored recipient meets the same 2001 `ConstraintHasOne` gate. Keeping the vault PDA as recipient requires its valid signer privilege, which an ordinary top-level signer cannot provide; the observed route uses Squads V4 execution. An approved Squads vault transaction is a separate authority prerequisite. The sampled outbound traces contain a direct claim for **one** of these 10 high-value off-curve escrows and none for the other nine; that sample does not prove those nine have never claimed or that no other authorized integration route exists. The Squads endpoint classifies their vault addresses but does not prove the current multisig approval configuration for each one. No permissionless Squads authorization path was established here.
