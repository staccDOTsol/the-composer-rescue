# Existing mainnet pool: local two-swap fee differential

On October 19, 2026, two independent **local mainnet-backed Surfpool forks** loaded existing Whirlpool pool `478r35b8cKMuj3HzxkwqWsx8vBfFLP5YhbkUEsWt2jfo` and its existing position `6K8ebAAheXRCfzSZo8zsdoaGJe2KzjTK8UPnci6Lrgm`. The position's liquidity was `18,439,611,894,805,844,217`, equal to all in-range pool liquidity; the targeted mainnet scan found one position for this pool. Token B is six-decimal USDC. [The script](real-mainnet-high-liquidity-pool.js) locally seeded a new swapper's USDC ATA with 50,000 raw units and signed **local fork transactions only**. No mainnet transaction was submitted.

Both forks had **identical decoded initial snapshots** and identical snapshots after a baseline permissionless position update. At baseline the position had `fee_owed_b = 94,637`, `fee_growth_checkpoint_b = 94,674`, and the USDC vault held 158,970 raw units. Each branch then sent two real B-to-A swaps of 20,000 raw USDC input. Each swap generated two raw USDC fee units and raised `fee_growth_global_b` by two Q64 units. The sole difference was the timing of the outsider's `update_fees_and_rewards` calls:

| Schedule | Global B growth | Final checkpoint B | Position owed B after baseline | USDC vault final | Swapper USDC final |
| --- | ---: | ---: | ---: | ---: | ---: |
| Update after each swap | 94,674 → 94,678 | 94,678 | 94,637 → **94,639** (+2) | 198,970 | 10,000 |
| Update only after both swaps | 94,674 → 94,678 | 94,678 | 94,637 → **94,640** (+3) | 198,970 | 10,000 |

All baseline, swap, and update `getTransaction` receipts have `meta.err = null` and actual Whirlpool `Swap`/`UpdateFeesAndRewards` logs. The signed local receipts and account snapshots are [interleaved](real-mainnet-high-liquidity-interleave.json) and [end-only](real-mainnet-high-liquidity-endOnly.json). Their initial and post-baseline snapshot objects compare exactly equal. Pool tick, liquidity, both vault balances, and both swapper token balances also match at the end of the branches. The interleaved branch credits the real position **one raw USDC unit (0.000001 USDC) less**; the unit stays in the vault without being credited to that position. This demonstrates the positive-owed checkpoint loss on an existing high-liquidity pool. It does **not** demonstrate a payout to the outsider or material economic impact.

The baseline transaction is separate and identical in both branches to isolate new swap fees from the position's older uncheckpointed growth. With `L` just below `2^64`, each `+2` fee-growth step computes `floor(L × 2 / 2^64) = 1` owed unit, then the partial checkpoint advances by `ceil(1 × 2^64 / L) = 2`. A single final update over `+4` growth credits `floor(L × 4 / 2^64) = 3` units. This is the same rounding mechanism as the controlled live-ELF test, now exercised against an already deployed pool and position.

## Attacker-owned LP and harvest check

After the victim's one-unit gap was established, [a second local script](real-mainnet-high-liquidity-new-lp.js) ran the same five real instructions on **each** fork: open an actor-owned position NFT, increase its liquidity by 100,000,000, permissionlessly update it, collect its fees, then decrease all its liquidity. Every signed local transaction returned `meta.err = null`. The new position's `fee_owed_a` and `fee_owed_b` stayed zero, and `CollectFees` transferred zero. The [interleaved](real-mainnet-high-liquidity-new-lp-interleave.json) and [end-only](real-mainnet-high-liquidity-new-lp-endOnly.json) receipts show identical final attacker balances: token A `2,091,934 → 2,091,933` and USDC `10,000 → 9,999`. Both vaults also have identical final balances across branches. The actor's one-raw-unit cost in each token arose during its deposit/withdraw cycle in **both** branches; it was not a payout of the victim's missing USDC unit. Victim `fee_owed_b` remained `94,639` versus `94,640`.

The source supports this limited result. [`CollectFees`](https://github.com/orca-so/whirlpools/blob/f2a3d13fa04eb15cf5b5a309ef9b226fd5d34e36/programs/whirlpool/src/instructions/collect_fees.rs#L14-L65) requires the position NFT's signed owner/delegate and transfers only `position.fee_owed_a/b`; [the v2 handler](https://github.com/orca-so/whirlpools/blob/f2a3d13fa04eb15cf5b5a309ef9b226fd5d34e36/programs/whirlpool/src/instructions/v2/collect_fees.rs#L16-L96) uses the same bounds. [`CollectProtocolFees`](https://github.com/orca-so/whirlpools/blob/f2a3d13fa04eb15cf5b5a309ef9b226fd5d34e36/programs/whirlpool/src/instructions/collect_protocol_fees.rs#L12-L50) requires the configured authority and transfers only `protocol_fee_owed`. [`DecreaseLiquidity`](https://github.com/orca-so/whirlpools/blob/f2a3d13fa04eb15cf5b5a309ef9b226fd5d34e36/programs/whirlpool/src/instructions/decrease_liquidity.rs#L27-L105) requires NFT authority and withdraws amounts computed from liquidity and price. [`Swap`](https://github.com/orca-so/whirlpools/blob/f2a3d13fa04eb15cf5b5a309ef9b226fd5d34e36/programs/whirlpool/src/instructions/swap.rs#L84-L128) computes the output from swap math; [its transfer routine](https://github.com/orca-so/whirlpools/blob/f2a3d13fa04eb15cf5b5a309ef9b226fd5d34e36/programs/whirlpool/src/util/swap_utils.rs#L59-L101) takes the trader's input before sending that computed output. Reward collection is separately NFT-authorized and capped by reward owed and reward-vault balance. No tested path paid the missing USDC unit to an outsider, new LP, or swapper, so this evidence supports **grief, not harvest**.
