# Real flash-loan Whirlpool v1 reproductions

These scripts use signed Solana transaction-v1 messages on a **local Surfpool mainnet-backed fork**. They contain actual Save, KLend, and Project 0 borrow/repay instructions and actual Whirlpool swaps and position updates. The only send paths require `http://127.0.0.1:48899` and check mainnet genesis before running. They never submit to Solana mainnet.

## Dependencies and fork

- Node.js with `@solana/web3.js` and `@solana/spl-token`. Set `ORCA_NODE_MODULES` to the directory containing those packages, or `WHIRLPOOLS_REPO` to a checkout with `node_modules`. `runtime.js` also checks the current directory and the local test checkout.
- The custom version-1 encoder and signer at `composer-runs/2026-10-15/hylo-exchange-v1-wire.js`.
- Surfpool 1.6.0 using a mainnet RPC datasource. Provide the datasource URL privately through `SURFPOOL_DATASOURCE_RPC_URL`; keep credentials out of command output and artifacts. Start the local fork with port 48899, websocket port 48900, and a distinct studio port, using `--no-deploy --no-tui --no-studio --yes --airdrop-amount 0`.

From the workspace root, run `node composer-runs/2026-10-19/orca-pr1396/real-flash-swap-roundtrip.js` for simulation-only two/three-provider round trips. Run `real-flash-send.js` on a fresh fork for a committed one-cycle three-provider transaction. Run `real-flash-cycle-ceiling.js` on a fresh fork to sweep and commit the strongest case with initialization in the flash transaction. Run `real-flash-cycle-optimized.js` on a fresh fork to commit a separate real margin/token-account setup transaction, sweep optimized flash transactions, and commit the strongest passing case. Each committed script uses deterministic actor/margin accounts, so start a fresh fork before rerunning it.

After `real-flash-cycle-optimized.js` on the same fork, run `real-flash-owned-liquidity.js` to open an actor-owned Whirlpool position with an NFT and then commit a three-loan v1 transaction with actual deposit and withdrawal. It reuses the optimized actor's prepared margin and WSOL/USDC accounts.

`real-flash-envelope.js` exports `buildFlashEnvelope` and `simulateFlashEnvelope` for arbitrary caller-supplied Whirlpool instructions. The builder patches indexed KLend and Save repay instructions and the Project 0 end index. It returns a signed serializable v1 wire, stats, lender account addresses, and instruction indexes. `initializeMargin:false`, `createWsolAta:false`, and `saveFeeTopup:false` let a separately prepared borrower omit setup instructions from the flash transaction.

## Receipts and limits

- `real-flash-send.json`: committed one-cycle Save/KLend/Project0 loan with two genuine swaps and two position updates. Transaction version 1, error null, 347,316 CU, 1,800 bytes, 19 instructions. All principal vault deltas are zero; Save fee vault rises 400 raw WSOL.
- `real-flash-cycle-ceiling.json`: committed four full 1-SOL/0.98-SOL round-trip cycles with three real lenders, 31 instructions, 2,238 bytes, 604,108 CU. A fifth full cycle fails `MaxInstructionTraceLengthExceeded`; 13 full cycles exceed the 64-instruction v1 builder limit.
- `real-flash-cycle-optimized.json`: committed real account setup followed by six full 1-SOL/0.98-SOL round-trip cycles within one three-lender v1 flash transaction. The flash transaction has 32 instructions, 2,347 bytes, 34 accounts, 734,208 CU, and zero principal vault deltas. A seventh cycle fails `MaxInstructionTraceLengthExceeded` at 751,286 CU and 2,493 bytes. Fourteen cycles encode as 64 instructions and 3,515 bytes but fail the same runtime trace limit; fifteen exceed the v1 instruction limit.
- `real-flash-compact-cycle.json`: a follow-on density check with one update after each forward swap and one final update still fails the trace limit at seven round-trip cycles. It uses 30 instructions, 2,397 bytes, and 754,518 CU; no unsuccessful case was sent to the local ledger.
- `real-flash-owned-liquidity.json`: a separate signed local-v1 setup transaction opened actor-owned position `BP3nUYtimwzFhG4UbVWjabkSHnsE2fVa9GR8xEgkyYMJ` with one position NFT. A committed signed v1 flash transaction (`5DZvhSZK9NT85XXKMqZncG3nHCZUuvEji1WguZKm7h8XSFMgiUkJMmLpdwicbX2pBVV5MNMJ3uQ24cWKRdstaAvd`) then performed three swaps, an increase of 1,000,000,000 liquidity units, a permissionless fee update, a decrease of the same liquidity, and all Save/KLend/Project0 repayments. `getTransaction` reports version 1, error null, 353,221 CU; the wire is 1,768 bytes with 14 instructions and 34 accounts. The signed-wire discriminators place increase at index 5 and decrease at index 8. Their CPI token transfers prove a real deposit of 18,095,002 raw WSOL and 3,765,023 raw USDC, followed by a withdrawal of 18,095,132 raw WSOL and 3,765,008 raw USDC. The amounts differ because an intervening swap moved the pool price. The position starts and ends at zero liquidity but its fee checkpoints move from zero to nonzero. Across the whole transaction, the actor's WSOL delta (−20,399,870 raw) plus the Whirlpool vault's (+19,999,870) plus Save's fee vault's (+400,000) equals zero; actor and pool USDC deltas are +1,987,246 and −1,987,246. All three lender principal vault deltas are zero. An additional `update_fees_and_rewards` after full withdrawal was tested and correctly failed `LiquidityZero` (6012); decrease already performs its Full checkpoint update.

The optimized flash transaction starts with 0.32 SOL in the actor's WSOL account, below its 1-SOL first swap input. Each real lender supplies 1 SOL. Six rounds debit the actor's WSOL by 0.12 SOL for net Whirlpool round-trip losses and 0.0004 SOL for Save's fee. The Whirlpool WSOL vault rises 0.12 SOL; its USDC vault drops 11,973,452 raw USDC units. The watched live LP position holds a negligible share of this large mainnet pool, so its owed/checkpoint fields do not move at these amounts even though the pool's fee growth and token vaults do. The separate controlled pre/post PR #1396 fixture in the parent `README.md` establishes the fee-checkpoint difference.

Surfpool truncates long execution logs. The receipts retain the returned logs and verify completed execution through `getTransaction` error null, transaction version 1, and committed before/after token-account and Whirlpool state. Surfpool's send path may try to fetch missing accounts upstream. The send scripts mark not-yet-created instruction accounts as zero-lamport fork-local System accounts before submission, which leaves them absent to account-creation instructions while avoiding that fetch behavior.

## Independently verified live ELF: high-liquidity fee loss

`surfpool_high_liquidity_live_elf.test.ts` runs the controlled high-liquidity scenario on a separate **offline** Surfpool instance. Each scenario creates its pool and positions under the exact source-built post-PR ELF, then `hot_swap_whirlpool_elf.py` replaces the ProgramData bytes with the independently verified current on-chain ELF before any tested swap, update, or collection. The helper replaces ProgramData to its exact new length and refreshes the executable account. A simple `surfnet_writeProgram` over the longer source ELF left trailing old code, so exact length verification is required. The live ELF SHA-256 is `94da79f11a6c57646c7483cbee37dbb135d91dbe4c2a6200e3ef24f4ca776273`.

On offline Surfpool port 49899, `high-liquidity-live-elf.json` and `.log` show 20 real swaps of 334 raw input units, each increasing fee growth by 2 at total liquidity 2^64. The target LP holds 3/4 of liquidity. With an outsider update after each swap, the target collected 20 raw units and both LPs collected 30; with only a final update, they collected 30 and 40. Token vault debits matched collections. The first live swap logged `Instruction: Swap` and consumed 31,114 CU; the first live fee update logged `Instruction: UpdateFeesAndRewards` and consumed 8,168 CU. This is a residual positive-owed fractional loss in the exact on-chain program, separate from the zero-owed issue that PR #1396 fixed.

To rerun, start a fresh offline Surfpool on a free port; load the source post ELF once with `deploy_and_verify.py`; copy `surfpool_high_liquidity_live_elf.test.ts` into `legacy-sdk/whirlpool/tests/integration/v1-ix/` of the built post checkout. From `legacy-sdk/whirlpool`, set `SURFPOOL_RPC_URL`, `LIVE_ELF_HOT_SWAP_SCRIPT`, `SOURCE_POST_ELF`, `LIVE_ONCHAIN_ELF`, and `RESULT_PATH` to the local paths, then run `node ../../node_modules/vitest/vitest.mjs run tests/integration/v1-ix/surfpool_high_liquidity_live_elf.test.ts --config vitest.config.mts`. The test swaps source/live ELF around each scenario and checks actual swap/update logs and collection amounts.
